# Continuing work with retained experience

18 September 2026. User-authorized follow-up in the existing study. The accepted
publication at `491c0f8a745f48327f6d095d2c3fa7f07d768b44` remains a completed
bounded result. Preserve its protocols, evidence, failed runs and conclusions.
Use separately identified protocols and evidence for this follow-up.

## Assignment and authority

Find a motivated continuing workload, implement the necessary environment, and
run an informative comparison of competent external reuse with the same available
experience plus weight updates. Start with bounded workload discovery and proceed
through development, acquisition diagnosis, fresh experiments and publication
when feasible. A proposal or benchmark catalogue alone does not fulfill this
assignment. You own workload selection, methods, sample sizes, implementation and
execution within the study's resources; routine decisions need no root approval.

The question remains what learned weights add when useful examples, corrections
and executable artifacts stay accessible. Preserve WC1–WC3 and append assessments.
The previous compiler ceiling is evidence about that finite language. It neither
requires more tuning on those fixtures nor forbids investigating a different
workload. No positive adapter result is required.

## Discover work before choosing a treatment

Inspect a small number of complete jobs from at least two plausible candidate
families. Recurring data-workflow maintenance and maintenance within an unfamiliar
codebase are starting leads, not mandatory domains. Prefer existing artifacts:
documented exports, schema changes, issues, patches, tests, failure reports and
task environments. Establish what the worker actually does and how correctness
can be checked before adapting a large benchmark or building infrastructure.

For each serious candidate, explain what earlier experience could teach, what
later decision it could improve, which ordinary tools already resolve the work,
and whether the remaining uncertainty is feasible for an available learner.
Use representative development examples to distinguish a broken environment,
inadequate basic model capability, a cheap explicit solution and potentially
useful accumulated experience. Select for an informative comparison, without
screening candidates on whether adapters win. Retain the reasons for rejection.

Real artifacts and constructed episodes can be combined. Preserve meaningful
dependencies, ambiguities, exceptions and changes observed in the source work.
Label authored scenarios and controlled variations; different names or amounts
do not create independent histories. Avoid adding vague prose, hiding mappings
or removing competent tools simply to make neural interpretation necessary.
Check historical cutoffs when replaying work so later solutions do not appear
in the worker's earlier environment.

The [source leads](sources/README.md#continuing-work-discovery-leads--18-september)
include BIRD-INTERACT, Continual Learning Bench and STATE-Bench. Root inspected
overviews and documentation, not their implementations or suitability for this
comparison. Inspect relevant methods, actual task instances, evaluation and
resource needs; pin versions before reuse. Explain whether existing research
answers, narrows or redirects the candidate question. A benchmark title is not
evidence that its tasks are observed real work or test continuing learning.

## Develop and run the identifying comparison

Build the smallest environment that preserves the consequential work. Use
Construct Runtime as an instrument where suitable, beginning from the verified
`9ffb10a66180626b80127fb1892b2cf71e39d946` boundary. You may select and verify a
newer revision, make an owned adaptation, or use another instrument with a stated
reason. Do not edit the derivative's active checkout or wait for its next release.
Choose a model and learning recipe suited to the workload and available resources;
the previous 4B model and 32-update recipe are not scientific requirements.

Give all conditions competent documentation access, search, execution, retained
examples and useful code. Develop the external-reuse baseline as seriously as
the learning treatment. Demonstrate behavioral acquisition on source/development
work; diagnose failed acquisition before interpreting a transfer null. Establish
feasibility and a concrete resource estimate before scaling experiments, then
continue autonomously when those checks support proceeding.

For the primary comparison, collect source experience under a declared collector
and feedback policy. At each comparison point, fork the same history and usable
artifact/tool snapshot into fixed-weight external reuse and external reuse plus
an adapter. Expose the exact eligible training evidence externally and verify the
access before interpreting results. Record actual retrieval and use: shared access
does not imply identical exposure. If later branches collect different histories
or acquire different tools, analyze that as a separate system comparison rather
than attributing the whole difference to weights.

Evaluate a chronological sequence with later source collection, fresh task probes
and a consequential change that preserves other obligations. Aim to exercise
more than one acquisition/update point and independently sourced histories within
resources; otherwise label the result as limited feasibility. Keep evaluation
answers and outcomes out of training, context and candidate selection. Choose
recipes on separate development material. Freeze the comparison before fresh
evaluation, preserving failed development and exploratory changes.

Record whether each update restarts from base on cumulative experience or
continues an adapter/optimizer. The original runtime supports the former. Check
compatibility with the current execution interface; training on an older action
format is a condition to examine, not an unnoticed difference. Separate worker
experience, teacher correction, authored reference trajectories and investigator
engineering in the provenance and costs.

If the agent itself discovers and builds a reusable implementation, that can be
a useful experience-retention result. Preserve and reuse it, measure its
construction and maintenance costs, and give both weight conditions comparable
access in the primary comparison. An investigator-supplied compiler establishes
available capability; an agent-acquired compiler makes a different acquisition
claim. Neither code retention nor a skill-file format is required in advance.

## Outcomes and continuation

Assess complete subsequent tasks, preserved obligations, useful behavior through
change and cumulative incurred work. Include collection, correction, tool
construction, training, retrieval, checking, selection, failures and repair.
Keep costs in native units and unknown costs visible. A stateless reference can
help identify the value of experience, but competent external reuse remains the
main comparison. Judge correctness from independently checked outcomes and
reproducible state or artifacts where possible; disclose any judging uncertainty.

Publish a concise account of workload choice, relevant public methods, original
expectations and their assessment, evidence and reproduction commands. Explain
what the results establish about acquired capability and where its value resides.
Keep the earlier publication identifiable and update README with current status.

Before standing down, assess the most promising next step: the uncertainty it
could resolve, why its answer could matter, available methods, cost and scope.
Pursue a useful bounded continuation within this remit without returning routine
method choices to root. Close a phase on explanatory progress, a demonstrated
limitation or a concrete resource constraint. If no suitable workload survives
the bounded search, publish the inspected examples and reasons; an explained
selection failure is useful. Publication alone is not a stop rule, and an open
broader question alone is not a reason for indefinite experimentation.
